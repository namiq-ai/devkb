# Pre-registration: confirmatory study of a software-process ontology served to coding agents

Frozen before any confirmatory task was generated. Its SHA-256 and the time it was frozen are recorded in
`PREREGISTRATION.sha256`; any later change is listed under "Deviations" in the paper.

## Background

An exploratory phase (461 agent runs on two internal repositories) built and tuned a development-process knowledge
graph (devkb), its query tools and "predefined packs" on six OCO tasks. Because the tools were changed after seeing
results on those tasks, the exploratory results are reported as exploratory only. This study tests the final design
on tasks generated afterwards, with a fixed protocol.

## Frozen system

- Extractors and tools: ODSF commit `ca2fb1e` (branch `feat/TL/ODSF-314-graph-audit-efficiency`), plus only the
  changes needed to run on a repository outside the factory registry (no change to extraction, ranking or replies).
- Graph snapshot per repository, built at the pinned commit of that repository.

## Tasks

Generated by `devkb/bench/oco_tasks.py` (generalised to repositories without role profiles) with seed **2027**, after
this document is frozen. Any function name used in an exploratory task is excluded. Per repository, up to four tasks
of each kind, chosen by the generator's rule, not by hand:

- **error → handler**: an error message raised once in non-route code; name the raiser, every route handler that
  reaches it through calls at any depth, and the test files on those paths.
- **change impact**: a function reached by three or more route handlers; those handlers, and the test files to run.
- **wide refactor**: a uniquely named function called from 8 to 25 files; the caller files and the test files among
  them (and, where the repository declares role boundaries, the files the role may not edit).

Truth: an import-resolved AST scan of the pinned commit (`devkb/bench/workflow_tasks.py`), never the graph. A task is
kept only when every function on its paths has a name defined once in the repository.

## Arms (same model and same task prompt in every arm)

| Arm | Tools beyond Read/Grep/Glob/read-only git | System-prompt addendum |
|---|---|---|
| plain | none | neutral work-efficiently note |
| core | 12 single-question graph tools | the general graph skill |
| workflow | the task toolset | the task's skill |
| lean | 7 tools: `rca_trace`, `impact`, `callers`, `tests_for`, `tests_to_run`, `review_pack`, `config` | a 120-word skill |
| pack | none; the prompt carries a pack built from the task's own inputs | neutral note (as plain) |

The graph arms are told to use the graph first. 40-turn cap, `--no-session-persistence`, one discarded warm-up run per
arm, runs shuffled with a fixed seed, three in parallel.

## Models and repetitions

- Primary: `sonnet` (claude-sonnet-5-5), all five arms, **5 repetitions** per task.
- Generality: `haiku` (claude-haiku-5-5), arms plain, lean and pack, **3 repetitions** per task.

## Outcomes

- **Primary, cost**: API-equivalent cost of a run (`total_cost_usd`). Effect of an arm = 1 − Σ_task mean(arm cost) /
  Σ_task mean(plain cost).
- **Primary, quality**: task score in [0, 1] against the truth (F1 of the named sets; exact match of the raiser).
- **Secondary**: turns, tool-result bytes, wall time, whether the graph was used.

## Hypotheses (Sonnet, pooled across repositories)

- **H1** pack costs less than plain, and its quality is non-inferior (margin 0.05).
- **H2** lean costs less than plain, and its quality is non-inferior (margin 0.05).
- **H3** core costs no more than plain (cost ratio ≤ 1.0), quality non-inferior.
- **H4** on error → handler tasks, pack and lean each cost less than plain.
- **H5** (Haiku) pack and lean cost less than plain.

## Analysis

- Cost effects with 95% bootstrap intervals, resampling runs within task (10,000 draws, seed 1); a one-sided
  Wilcoxon signed-rank test over per-task mean differences. Holm correction across H1 to H4 (cost); H5 separately.
- Quality: mean difference with 95% bootstrap interval; non-inferior when the lower bound exceeds −0.05.
- Per repository and per task kind reported descriptively, without further tests.
- Invalid runs (no parseable answer, error, timeout) are kept: score 0, cost as recorded. No run is repeated.
- Score noise is estimated by the spread between repetitions of the plain arm.
